# 0002 apiのフレームワークにHonoを使う

- 状態: 採用
- 決定日: 2026-09-30

## 背景

apiは、切り出し元のプロジェクトからExpressを引き継いでいた。Expressを選んだ理由は記録されていない。WorkersでExpressを動かすため、次のものが必要だった。

- `cloudflare:node`の`httpServerHandler`と、実際にはソケットを開かない`app.listen()`。
- Workerの`env`を`cloudflare:workers`から取ること。Expressのハンドラは`env`を引数で受け取らない。
- Better Authのハンドラを`express.json()`より前に置くこと。Better Authは生の本文を自分で読む。

Workerを束ねた結果は約3MB(gzipで約630KB)で、そのうち約1MBがExpressとその依存(iconv-lite、mime-dbなど)だった。

また、この雛形では、同時に書き換わる状態を持つゲームにDurable Objectsを使う(READMEを参照)。WebSocketをDurable Objectへ渡すには、WorkersのRequestをそのまま`stub.fetch()`へ渡す必要がある。Expressのハンドラからは、WorkersのRequestを扱えない。

## 決定

apiのフレームワークにHonoを使う。

- `/api/auth/*`はBetter Authの`auth().handler(c.req.raw)`へそのまま渡す。
- Workerの`env`は`c.env`で受け取る。
- 主体のユーザーIDは`c.get("userId")`で渡す。アプリ全体の型は`AppEnv`(`packages/api/src/session.ts`)に1つだけ置く。

## 採らなかった案

- Expressを続ける案: 背景に挙げた回避策、Workerの大きさ、Durable Objectsとのつなぎにくさが残るため採らない。
- フレームワークを使わず素の`fetch`ハンドラで書く案: 依存は減るが、ルートの振り分け、ミドルウェア(`attachUser`・`requireUser`)、JSONの応答を自前で書くことになる。ゲームごとにルートを足していくので、その部分が膨らむ。Honoはこの範囲を数十KBで担うので、依存を1つ足す方を選ぶ。

## 結果

- Workerはgzipで約350KBになった。残りの大半はBetter Authとその依存(kysely、zodなど)。
- APIの形とエラー応答の`{error}`は変わらないので、webは変更しない。
- `nodejs_compat`は残す。Better AuthがWorkersでは`node:async_hooks`のAsyncLocalStorageを使うため。
- [ADR 0001](0001-workers-static-assets.md)で`@cloudflare/vite-plugin`を採らなかった理由のうち、「Express on Workersがこのプラグインの上で動くかの検証も要る」は当てはまらなくなった。依存が増えることと、現在の転送で困っていないことは変わらないので、結論は変えない。
