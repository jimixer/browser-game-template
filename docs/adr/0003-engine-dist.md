# 0003 apiとwebはルール層のビルド結果を読む

- 状態: 採用
- 決定日: 2026-09-30

## 背景

これまで、`game-rule-engine`の`main`と`types`は`src/index.ts`を指していた。apiとwebは、wrangler(esbuild)とviteでTypeScriptのソースをそのまま束ねていた。`dist/`はルール層のテストをNodeで実行するためだけにあった。

この形は、Node自身がルール層を読まない場合にしか成り立たない。

- Nodeは型を取り除いて`.ts`を実行できるが、`import "./types.js"`を`types.ts`へ読み替えない。ルール層のファイルを分けてNodeの流儀で`.js`と書くと、`ERR_MODULE_NOT_FOUND`で止まる。手元でNode 24を使って再現した。
- テンプレートでは、ルール層のファイルが1つで、apiにテストがなかった。そのため問題が表に出なかった。
- apiのテストやカバレッジの計測をNodeで`dist/`から実行するゲームでは、その中でルール層を読むところで壊れる。

ゲームが育てば、ルール層のファイルを分け、apiにテストを足すことになる。テンプレートでも、いずれ同じ問題に当たる。

## 決定

ルール層の`main`と`types`を`dist/`(`index.js`と`index.d.ts`)に向ける。apiとwebは、ビルド済みのルール層を読む。

- `npm install`と`npm ci`の`prepare`でルール層をビルドする。cloneしてすぐでも`dist/`がある。
- `npm run dev`は、開発サーバーの前に一度ビルドし、その後は`tsc -w`で作り直し続ける。wranglerとviteは作り直された`dist/`を読み直す。
- `deploy.sh`は、最初にルール層をビルドする。
- `declarationMap`を出力する。エディタで定義へ移動すると、`.d.ts`ではなく`src/`が開く。

## 採らなかった案

- `src/`を指したまま、ルール層の中の相対importを`.ts`拡張子で書く案: Nodeが`src/`を直接読めることは確かめた。一方で、Nodeが型を取り除けない構文(`enum`など)が使えなくなる。ルール層のimportもすべて`.ts`で書き続けることになる。制約が大きいため採らない。
- `src/`を指したままにする案: 背景のとおり、ルール層を分けてNodeから読んだ時点で壊れるため採らない。

## 結果

- ルール層を変えたら、ビルドし直すまでapiとwebに反映されない。`npm run dev`の中では`tsc -w`が作り直す。開発サーバーを動かしたままルール層を書き換え、apiの応答が変わることを確かめた。
- 開発サーバーの外でapiの型検査などを走らせるときは、先に`npm run build --workspace game-rule-engine`が要る。
- Nodeで実行するapiのテストを足しても、ルール層は`dist/`から読まれる。ファイルの分け方やimportの書き方を、テストのために変えなくてよい。
